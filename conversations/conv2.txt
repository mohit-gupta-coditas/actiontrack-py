    ## 1. Purpose
    Turn one markdown file into either a `NoteMeta` (meeting date, title, raw attendees, numbered body lines) or a `SkipRecord`
    explaining why the note is unusable. A pure function apart from reading the file. **It never raises for content problems.**
    
    ## 2. Interface
    
    ```python
    def load_note(path: Path, *, date_order: Literal["DMY", "MDY"] = "DMY") -> NoteMeta | SkipRecord
    def parse_meeting_date(text: str, *, date_order: Literal["DMY", "MDY"]) -> date | None   # reused by tests / M3
    ```
    
    ## 3. Processing rules (in order)
    
    | Step | Rule | On failure |
    |---|---|---|
    | 1. Read | `path.read_bytes()`. The file is opened read-only and never written (REQ-GEN-03) | `OSError` → `READ_ERROR` (detail = the error message) |
    | 2. Empty | 0 bytes, or only whitespace after decoding | `EMPTY_FILE` |
    | 3. Binary | A NUL byte in the first 8 KiB | `BINARY_FILE` |
    | 4. Decode | `utf-8-sig` (BOM removed) | `UnicodeDecodeError` → `INVALID_ENCODING` (detail = byte offset) |
    | 5. Normalize | `\r\n` and `\r` → `\n` | — |
    | 6. Hash | `sha256` of the **raw bytes** (before decode) | — |
    | 7. Frontmatter | If line 1 is exactly `---` (trailing whitespace allowed): find the next line that is `---` or `...`. YAML-parse the block with `yaml.safe_load` | No closing fence, YAML error, or a result that isn't a mapping → `INVALID_FRONTMATTER`, `line_no` = the YAML error line (offset into the file) |
    | 8. Body | All lines after the frontmatter (or every line if there is none), keeping the **original file line numbers** | — |
    | 9. Meeting date | The first one found from: (a) frontmatter `date` (a YAML date or a string); (b) a body line matching `^\s*\**date\**\s*:\s*(.+)$` (case-insensitive) before the first checkbox line; (c) the first H1 (`# …`) containing a date substring | No candidate → `MISSING_DATE`. Candidate but `parse_meeting_date` gives None → `UNPARSEABLE_DATE` (detail = the raw value) |
    | 10. Title | Frontmatter `title`, else the H1 text with the date and separators (`—`, `-`, `:`, `|`) removed, else None | — |
    | 11. Attendees | The first one found from: (a) frontmatter `attendees` / `participants` (a list, or a string split on `,`/`;`); (b) a body line `Attendees:` / `Participants:` (case-insensitive, optional bold) with a `,`/`;` list; (c) a heading `## Attendees` / `## Participants` followed by a bullet list (ends at the next heading or a blank line after the bullets). Entries are trimmed, empties dropped, order kept | No non-empty entry → `MISSING_ATTENDEES` |
    
    ### `parse_meeting_date`
    1. If the text contains an ISO date `\d{4}-\d{2}-\d{2}` → `date.fromisoformat`.
    2. Else `dateparser.parse` (lazy import) with `{"STRICT_PARSING": True, "DATE_ORDER": date_order, "PREFER_DAY_OF_MONTH": "first",
       "REQUIRE_PARTS": ["day", "month", "year"]}`, so a meeting date must have day, month **and** year.

    ## 1. How we work
    
    Every module goes through the same steps, in this order:
    
    1. **Spec**: `modules/<M>/spec.md` is reviewed and marked *Approved*. Any change to the root spec is made there first.
    2. **Tests (red)**: every test case in `modules/<M>/tests.md` is written as a pytest test whose name contains its TC ID
       (e.g. `test_TC_M3_04_weekday_same_day_rolls_to_next_week`). They all fail.
    3. **Implement (green)**: work through `modules/<M>/tasks.md` in order, ticking tasks off as they pass.
    4. **Gate**: the module's Definition of Done (below) passes. Update the status board in §4.
    5. **Merge**: branch `feat/<m-id>-<name>` → PR → `main`. The PR description links the module spec and lists its TC IDs.
    
    ### Definition of Done (every module)
    - All TCs in the module's `tests.md` are implemented and passing.
    - `ruff check`, `ruff format --check` and `mypy --strict actiontrack` are clean.
    - Line coverage of the module's package is ≥ 90% for the pure modules (M1–M5, M9), and ≥ 80% for the others.
    - No public interface differs from the spec. If it had to, the spec was updated first (in the same PR).
    - Every REQ ID the module owns appears in at least one TC.
    
    ### Conventions
    - **IDs**: requirements `REQ-<AREA>-NN` (root spec §18) · modules `M0`–`M12` · tasks `T<m>.<n>` · test cases `TC-M<m>-NN`.
    - **Test locations**: `tests/unit/<package>/` for unit tests, `tests/integration/` for anything that touches SQLite, the file system or MCP,
      `tests/e2e/` for M12. Shared fixtures live in `tests/fixtures/notes/<scenario>/`.
    - **Markers**: `@pytest.mark.slow` for perf/e2e. The default `pytest` run excludes slow tests, and CI runs everything.
    - **Time**: tests never read the real clock. They use `FixedClock` (M0).

    52:## 4. Input Format (Meeting Notes)
    54:### 4.1 Expected structure
    ### 4.1 Expected structure
    
    A note is accepted when it contains a **meeting date**, an **attendees list** and free-form body text.
    Both of these layouts are supported:
    
    **A. YAML frontmatter (preferred)**
    ```markdown
    ---
    date: 2026-11-18
    title: Q4 pricing sync
    attendees:
      - Priya Shah <priya.shah@coditas.com>
      - Priya Nair
      - Rahul Mehta
    ---
    ## Notes
    ...free text...
    - [ ] Priya Shah to send the revised quote by Friday
    - [x] Rahul to book the venue
    ```
    
    **B. Heading / inline fields (fallback)**
    ```markdown
    # Q4 pricing sync — 2026-11-18
    Attendees: Priya Shah, Priya Nair, Rahul Mehta
    ```
    
    Meeting dates are parsed with `dateparser` using `STRICT_PARSING=True` and `DATE_ORDER=DMY` (team convention, configurable).
    ISO `YYYY-MM-DD` is always tried first. The meeting date may come from: the frontmatter `date`, a `Date:` line, or a date in
    the first H1 heading. If none of these exists, the note is malformed.
