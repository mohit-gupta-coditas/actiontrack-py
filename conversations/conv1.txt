I've written the spec to [spec/requirements.md](spec/requirements.md), based on your answers.

**What you decided:**
- **Stack:** Python 3.11+ with a Typer command line and a local SQLite file for storage.
- **Gmail:** the CLI connects to the Gmail MCP server itself and can only call `create_draft`. Any other tool name, such as send, reply or forward, is blocked in code, and the tests check this.
- **Emails:** built from a fixed template, so the same input always gives the same email.
- **Dates:** relative dates like "by Friday" are worked out from the meeting date in that note.
- **Duplicates:** an exact match after cleaning up the text, then fuzzy matching (same owner, similarity score of 88 or more). When dates conflict, the latest meeting's due date wins, and every source file is kept.
- **Two Priyas:** the name is matched against that note's attendee list. If it's still unclear, the item is flagged `ambiguous_owner` instead of being assigned.
- **Missing owner or due date:** the item is still stored, with a flag. Items with no due date are never counted as overdue.
- **Malformed notes:** a missing date, missing attendees or broken frontmatter/encoding skips the whole note. A bad checkbox skips just that line. Everything skipped is reported and ingest never crashes.
- **Re-running ingest:** files that haven't changed are skipped, and items you marked done in the CLI are never reopened.
- **Item IDs:** a 6-character hash, and `done` accepts any unique prefix.
- **Email addresses:** the attendee's email from the note if there is one, otherwise `firstname.lastname@coditas.com`. If only a first name is known, `followup` stops with an error and creates no draft.

**The spec also covers** the parsing steps, the database tables, each command's options and exit codes, the folder layout, error handling, the test plan and 9 acceptance criteria.

**Decisions I made myself.** Section 16 lists them as Q1–Q8; these are the ones most worth checking:
- **Q1:** "by Friday" in a note from a Friday meeting means the following week's Friday.
- **Q2:** if a later note shows an item you already marked done as open again, it stays done.
- **Q6:** we still need the actual Gmail MCP server's launch command or URL; it's a config setting for now.
- **Q8:** dates like `03/04/2026` are read day-first (3 April).

I've added a CLI best-practices section to [spec/requirements.md](spec/requirements.md) as §13, based on the conventions at clig.dev. It's written as requirements the build has to meet, not optional advice.

**What §13 covers:**
- **Packaging:** a standard Python project file with an `actiontrack` command, installable with `pipx` or `uv`, locked dependencies, version numbers, and `--version`.
- **Command design:** the same flags mean the same thing in every command, nothing ever waits for input so it can run in scripts, re-running commands is safe, and `followup` has a `--dry-run`.
- **Help:** every command's `--help` shows at least one example, shell tab-completion is available, and a mistyped command suggests the right one.
- **Output:** data goes to stdout and everything else to stderr, so `list --json` can be piped cleanly. Colour only appears in a terminal, `NO_COLOR` is respected, the JSON format is versioned, and there are `-q` and `-v`/`-vv` levels. Windows output is forced to UTF-8.
- **Errors:** short messages that say what to do next, no Python traceback unless `--debug` is set, fixed exit codes, and Ctrl-C undoes the current database write and exits with code 130.
- **Configuration:** command-line flags override environment variables, which override the config file, which overrides defaults. Files go in each operating system's standard folders, and a new `config show` command prints the settings in effect.
- **Speed:** `list`, `done` and `--help` should start in under 300 ms, so slow libraries are only loaded by the commands that need them. The spec also lists the database indexes.
- **Robustness:** works the same on Windows, macOS and Linux, handles different line endings and file encodings, and a second copy running at the same time waits instead of failing.
- **Code structure:** the CLI file only reads arguments and prints results; errors are mapped to exit codes in one place.

**Changes elsewhere to match:**
- **Paths:** the database, config file and failed-email folder no longer sit in a hard-coded `~/.actiontrack`; they use each operating system's standard locations.
- **Global flags:** added `-q`, `--debug`, `--version` and `-h`.
- **Acceptance criteria:** added two new ones, for clean `--json` output and no tracebacks on user errors.
- **Numbering:** the later sections moved down by one, and the cross-references are updated.
